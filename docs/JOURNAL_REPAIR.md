# 桌面 Journal 修复

桌面启动时检查数据库。数据库丢失或为空且存在登记过的备份记录，或者 SQLite 明确报告数据库损坏时，先在独立目录重建候选数据库，再显示采用确认。权限错误、数据库被占用、磁盘满或更新版本的数据库不会被当作损坏来替换。

修复使用默认备份目录和数据目录中的 `backup-locations.txt`。损坏数据库没有可用的登记备份时，可以选择一个备份根目录。若整个数据目录都丢失且外部备份位置也不再登记，应用正常启动（新的空数据库），之后在设置 › 高级用“从备份文件夹找回历史…”选择备份位置或其中某个操作的文件夹：缺少的操作被读回、备份默认保留，中断的操作照常进入恢复；该位置随即登记，之后的重建无需再指定（`mm-cli rebuild-journal --from DIR` 相同）。

确认前，`journal-repair-<随机标识>` 保存原 DB、WAL、SHM 的副本、独立候选数据库和 `preview.json`。预览显示导入和跳过数量、保留位置以及设置和自定义预设无法重建的限制。取消不会采用候选数据库，保留目录也不会自动删除。恢复出的备份默认设置为保留，避免丢失旧保留标记后自动清理。

采用前重新核对原文件、候选数据库和保留副本的哈希；内容改变会拒绝采用。替换前写入并刷新 `journal-repair.pending.json`，随后移开附属文件，再替换数据库。中断标记存在时禁止普通启动，重新启动需确认继续先前的替换。单实例锁覆盖检查、预览和采用；提权运行拒绝修复。链接、云文件和多个硬链接的输入被拒绝。

重建步骤读取备份记录，不读取或改写照片。采用后普通启动恢复仍可能根据中断的操作记录处理照片，因此确认文案明确区分数据库修复和后续操作恢复。

已验证：合成损坏/丢失数据库、取消、提权拒绝、候选或原文件变更、单实例占用、路径越界以及三个替换边界中断后的继续。边界测试保留合成附属文件字节，不代表真实掉电或真实 SQLite WAL 重放验证。原生确认框已编译并通过注入选择测试，尚未进行手动桌面验收。所有验证在临时数据目录执行。
